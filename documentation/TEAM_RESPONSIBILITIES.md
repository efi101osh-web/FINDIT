# FINDIT: Team Responsibilities

> **Status:** Stage 1 draft. Fill in the names. Everything here is a *suggestion* you can reassign.

## 1. How the work is organised

FINDIT is built by **one developer, the group leader, working with an AI coding assistant**. The group leader implements, integrates, tests and publishes all of the code (backend, database, mobile app, admin dashboard) and owns the GitHub repository.

The other group members have important **non-coding** roles. **No coding tasks are assigned to them, and no development work waits on them.** That keeps the codebase consistent and avoids Git conflicts.

## 2. Roles

| Role | Person | Responsibilities |
|---|---|---|
| **Group leader and developer** | *[name]* | All coding, architecture, integration, GitHub, environment setup, technical documentation, deployment for the demo |
| **Presentation lead** | *[name]* | Slides, speaking order, story of the project, rehearsals. Needs to understand [PROJECT_OVERVIEW.md](PROJECT_OVERVIEW.md) and the demo script |
| **Quality and user testing** | *[name(s)]* | Run the manual test checklists in [TEST_PLAN.md](TEST_PLAN.md) with the developer present, record what they observe, and report problems. Try to "break" the app like a real user |
| **Documentation and report** | *[name]* | Proofread the documents, write the academic report from them, prepare the [USER_GUIDE.md](USER_GUIDE.md) wording. They send edits to the developer instead of committing files themselves |
| **Demo and test data** | *[name]* | Write realistic *fake* lost/found stories for demo data (no real names, phone numbers or ID numbers) and plan the demo sequence |
| **Requirements reviewer** | *[name]* | Read [REQUIREMENTS.md](REQUIREMENTS.md) and check it against the assignment brief and marking criteria |

One person can hold several roles.

## 3. Ways teammates can help without touching code

- Read the documents and flag anything unclear or missing.
- Join test sessions (in person or screen-share) and follow the checklists.
- Write the narrative for the final presentation and rehearse the demo.
- Suggest realistic campus locations and categories for the lists in [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md).
- Report bugs as short written notes: what they did, what they expected, what happened, and a screenshot (with no real personal data).

## 4. Working agreements

- Only the developer commits code to the repository.
- Bug reports and suggestions go to the developer in writing (a shared note or GitHub Issues if they have accounts).
- Anything involving real personal data stays out of the repository, screenshots and chat.
- Decisions that change the project's scope are recorded in [DECISIONS.md](DECISIONS.md).
